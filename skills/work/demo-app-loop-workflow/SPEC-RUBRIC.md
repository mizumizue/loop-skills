# Demo App ルーブリック（開示参照）

`demo-app-loop-workflow` の Verifier 正本。指揮者と作業者は該当工程でここを Yes/No する。  
曖昧な「品質確認」だけは不合格。

**Leading words:** sector brief · business spec · screen spec · system spec · manifest · demo-seeded · test-check · conformance · demo-launch · host-forward

## ねらい

テーマ語の連想や汎用 CRUD で止めない。業務アプリでは **業態 → 業務 → 画面 → システム** の4層を先に固め、技術選定・実装・デモテスト・適合検証・ホスト公開起動へ進む。  
人間に確認せず **AI が調べて決める**（hands-off）。薄い作文はゲート不合格。最終報告では **ホストから開けるデモ URL** を必ず出す。

## demo-grade（方針）

- **原則:** 工程2–5で採用した事項は **すべて実装対象**（`manifest` の `implement` 行）。調査で **明示見送り** と記録したものだけ実装しない。
- **非目標:** 認証本番・決済本番・外部配信本番・ブランド最終仕上げ・マルチテナント等は不要。これらを理由に採用機能を落とすのは No。
- **黙って落とす禁止:** 未実装が許されるのは manifest で `deferred` と根拠パスがある場合のみ。根拠なしの未実装は工程7不合格。
- **デモテストは必須・単体緑は不要:** 工程8でスモーク／クリティカルパス自動実行が必須。単体テスト緑・`quality/`・Audit は成功条件に含めない。

## システム仕様・統合（工程5 · T1–T8）

`system-spec.md` と `scope.md`（統合版）に対する検証。

| ID | Yes の条件 |
|----|------------|
| T1 | **利用者（actors）** が2役以上。各役の主ジョブ1文。brief／business-spec の帰結である |
| T2 | **actor-split:** 役ごとに主表面が別 |
| T3 | **surface budget:** 主要ハッピーパスは **表面 ≤3** |
| T4 | **demo-seeded:** 当該システムに即した事前選択肢／初期選択の方針が具体 |
| T5 | `system-spec.md` に非機能要件（性能・可用性・データ永続化方針）が ≥3 項目ある |
| T6 | `system-spec.md` にデータモデル概要（主要エンティティ ≥3）と境界（内部／外部）がある |
| T7 | `scope.md` に `## implementation manifest` が存在し、A–D の4表が揃う（下記） |
| T8 | screen-spec の採用行が manifest または `deferred`＋根拠に **1:1** で落ちている |

### implementation manifest（T7 正本）

| 表 | 列（最低限） | 抽出元 | デフォルト status |
|----|-------------|--------|-------------------|
| **A Actor 到達** | ID・actor・demo-seeded ペルソナ・主表面・到達方法 | T1／screen-spec actors | `implement` |
| **B UC／WF** | ID・WF・ジャーニー ID・完結表面・操作1文 | business-spec WF・screen-spec 遷移 | `implement` |
| **C 例外フロー** | ID・決め事 ID・状態／分岐・操作する役・主表面 | business-spec 例外 | `implement` |
| **D 可変境界** | ID・境界名・変更する役・主表面・操作1文 | business-spec B3 採用行 | `implement` |

`status` は `implement` または `deferred` のみ。`deferred` には **見送り根拠パス** 列を必須とする。

## デモテスト（工程8 · Q1–Q5）

`test-check.md` に対する検証。実装直後の動作不具合を自動で潰す。文書突合だけでは No。

| ID | Yes の条件 |
|----|------------|
| Q1 | `RUN/test-check.md` が存在し、実行コマンド・終了コード・失敗時ログの有無が書かれている |
| Q2 | manifest の **`implement` 行すべて**について、スモークまたはクリティカルパスの自動検証行がある（行数一致） |
| Q3 | 自動検証が **終了コード 0**（起動→操作→期待結果まで。HTTP 4xx/5xx・未到達・期待状態不一致は Fail） |
| Q4 | **重大バグ＝0**（クラッシュ・主ボタン無反応・権限無視・永続化失敗・主 WF 未完遂は重大） |
| Q5 | `implement-reachability.md` の操作パスとテスト手順が矛盾しない（矛盾があればどちらかを直し再実行済み） |

### test-check.md（工程8 必須出力）

```markdown
## デモテスト結果
| Manifest ID | 自動手順（≤5） | 期待 | 結果 | 重大? |
|-------------|----------------|------|------|-------|
```

- 手段はスタックに合わせる（例: `npm run verify`、API シーケンス、ヘッドレスブラウザ）。手段の有無を人間に聞かない。
- Fail 時は同一工程で修正→再実行。Stop 内で直らなければ工程7へ戻す。

**工程8 Pass 条件:** Q1–Q5 すべて Yes。重大バグが 1 件でもあれば不合格。

## デモ起動・公開（工程10 · L1–L5）

`demo-launch.md` と実際に listen しているプロセスに対する検証。人間がブラウザで見るための最終工程（Runログの直前）。

| ID | Yes の条件 |
|----|------------|
| L1 | `demo/` が **バックグラウンドで起動中**（作業終了後もプロセスが残る） |
| L2 | サーバーが **`0.0.0.0`（または全インタフェース）** で listen。`127.0.0.1` のみバインドは No |
| L3 | ヘルスまたはトップ URL が HTTP 200（`demo-launch.md` に確認コマンドと結果） |
| L4 | **WSL 判定時**（`/proc/version` に Microsoft または WSL）: ホスト（Windows）向け URL とフォワーディング手順／実施結果が `demo-launch.md` にある。未実施は No |
| L5 | `demo-launch.md` に **ホスト向け URL（必須）**・WSL 内 URL・ポート・起動コマンド・停止方法がある |

### WSL ホスト公開（L4 正本）

1. UI／API とも `--host 0.0.0.0`（または同等）で起動する。
2. 既定のホスト向け URL は `http://localhost:<port>/`（WSL2 の localhost フォワーディングを利用）。
3. `localhost` から届かない場合は次を実施し記録する:
   - WSL 側 IP を取得（例: `hostname -I`）し `http://<wsl-ip>:<port>/` を併記
   - 必要なら Windows 側 portproxy（管理者）例:  
     `netsh interface portproxy add v4tov4 listenaddress=0.0.0.0 listenport=<port> connectaddress=<wsl-ip> connectport=<port>`
4. ホスト側から到達確認できた URL を「人間用」として1本に確定し、最終報告でも同じ URL を出す。

### demo-launch.md（工程10 必須出力）

```markdown
## デモ起動
- 環境: WSL / 非WSL
- バインド: 0.0.0.0:<ports>
- ホスト向け URL: http://localhost:<port>/
- WSL 内 URL: ...
- フォワーディング: 実施内容または「localhost フォワーディングで到達確認済み」
- 起動コマンド: ...
- 停止方法: ...
- ヘルス確認: コマンドと HTTP 200
```
